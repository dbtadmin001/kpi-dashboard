A marketplace where business users never meet a fact table

Certified business views over Iceberg, served by Trino, catalogued in OpenMetadata and defined once in dbt semantic models. Physical tables stay hidden and read-only; personal sandboxes cost almost nothing; every query is audited.

03

Trino catalog configuration

The mechanism that makes hiding work is a property of Trino views, and it is worth stating plainly because the whole design rests on it:

A Trino view executes with the privileges of its owner, not its caller (DEFINER security, the default). So a business user can read marketplace.quality_metrics while holding no grant at all on nda_gold.fact_gmp_activities. That is what allows the physical schemas to be denied outright rather than merely left off a menu.

File-based access control, generated from the product declaration. Deny is the default:

{
  "catalogs": [
    { "group": "administrator|data_engineer", "catalog": "iceberg", "allow": "all" },
    { "group": "(business_user|analyst|...)", "catalog": "iceberg", "allow": "read-only" },
    { "catalog": ".*", "allow": "none" }
  ],
  "schemas": [
    { "user": "(.*)", "schema": "sandbox_\1", "owner": true },
    { "group": "(...)", "schema": "marketplace", "owner": false },
    { "schema": ".*", "owner": false }
  ],
  "tables": [
    { "group": "(analyst|data_scientist)", "schema": "nda_gold", "privileges": ["SELECT"] },
    { "group": "(analyst|...)", "schema": "marketplace",
      "table": "quality_metrics", "privileges": ["SELECT"] },
    { "privileges": [] }          // default deny: unmatched is invisible
  ]
}
  • Denied means invisible. Trino filters SHOW SCHEMAS and SHOW TABLES by permission, so a business user does not see nda_gold listed and cannot reach it by typing its name either.
  • Read-only production falls out of the same rules: no role below data engineer holds INSERT, UPDATE or DELETE on the physical schemas.
  • One catalog, not two. A separate marketplace catalog over the same REST endpoint would duplicate catalog metadata and let the two views of the world diverge. Permissions are the right separation.
Not yet enabled on this deployment. The rules file is generated and reviewable, but Trino's access control is engine-wide and this Trino is shared with another project, so switching it on would govern their catalogs too. It needs a dedicated Trino for the marketplace — the same gap recorded in the platform's risk list.

RBAC model

Roles are Keycloak groups, carried in the OIDC token, and mapped to Trino rules. The same group claim drives OPA for the API, so one membership change moves every surface at once.

Data EngineerAll 5 + authoringAll, read-writeFullVS Code, dbt
AdministratorAll + grantsAll, read-writeFull, all usersEverything

Business users never receive a grant on a physical schema at any point — not a masked one, not a filtered one. They read views, and the view reaches the data on their behalf.

05

Sandbox strategy

Every user gets sandbox_<username>, which they own outright. The storage answer is to make the cheap thing the default and the expensive thing deliberate.

ArtefactStoragePolicy
View (default)~600 B metadataUnlimited. Costs nothing, recomputes on read
Derived table (CTAS)real bytesPer-user quota; TTL; snapshot expiry

Measured: a sandbox view over a marketplace product occupies 576 B and returns 90 rows. The same result materialised as a table would write Parquet data files.

  • Steer to views. The sandbox command says so on creation, and the UI offers "Save as view" before "Save as table".
  • Quota and TTL on tables. A scheduled job drops derived tables untouched for N days and expires their snapshots, so abandoned experiments do not accumulate.
  • Sandboxes never feed production. Nothing in marketplace may reference a sandbox schema; promotion means a reviewed change to the product declaration.

API for the KPI UI

The UI never writes SQL. It asks for metrics by name and receives rows plus provenance.

POST /v1/auth/loginExchange SSO credentials for a tokenKeycloak password or auth-code grant
GET /v1/meIdentity and entitlementDrives which tabs render
GET /v1/productsCertified products this caller may seeTitles, descriptions, owners, certification
GET /v1/products/{'{'}name{'}'}/schemaDimensions and measuresBuilds the query UI without SQL
POST /v1/queryMetric query: measures, dimensions, filtersCompiled to Trino SQL server-side
GET /v1/metricsSemantic-layer metric listFrom dbt MetricFlow
POST /v1/exportCSV or Excel, entitlement-cappedRow cap per role
GET /v1/searchDiscovery pass-throughOpenMetadata search
GET /v1/suggestionsfuture AI-suggested queriesMetadata in, candidate queries out
 
POST /v1/query
{
  "product":    "delay_analysis",
  "measures":   ["avg_waiting_days", "pct_time_waiting"],
  "dimensions": ["workflow_stage", "process"],
  "filters":    { "process": ["GMP"], "arrival_month": { "gte": "2026-01" } },
  "order_by":   [{ "field": "avg_waiting_days", "desc": true }],
  "limit":      50
}

The request names business concepts only. The server resolves them against the product definition, rejects anything not declared, and emits parameterised SQL — so the UI cannot express a query that reaches a physical table, and cannot inject SQL either.

07

OpenMetadata integration

  • Ingestion reads the Trino catalog, so certified views appear as first-class assets beside the tables.
  • Certification via tier tags: marketplace views Tier.Tier1, physical schemas Tier.Tier3–Tier5. Tier drives search ranking as well as the badge.
  • Ownership from the product declaration — each product names an owning team, so the catalogue always has someone to ask.
  • Lineage declared product → source, published as OpenLineage to both Marquez and OpenMetadata from one graph definition.
  • Search works because descriptions carry the questions and synonyms people type. The existing platform measured 12/12 lay-language queries returning the correct table after that treatment.
The same vocabulary everywhere. Product titles, descriptions and synonyms live in marketplace/products.py and are pushed to OpenMetadata, so the name in the catalogue, the view in Trino and the metric in dbt cannot disagree.
08

dbt Semantic Layer

Semantic models and metrics are generated from the same product declaration that creates the views — 19 metrics across 5 products, so a measure cannot exist in one place and not the other. 

semantic_models:
  - name: delay_analysis
    model: ref('delay_analysis')
    defaults: { agg_time_dimension: arrival_month }
    dimensions:
      - { name: workflow_stage, type: categorical }
      - { name: arrival_month,  type: time, type_params: { time_granularity: month } }
    measures:
      - { name: avg_waiting_days, agg: average, description: "Mean days queueing" }
metrics:
  - name: delay_analysis__avg_waiting_days
    type: simple
    type_params: { measure: avg_waiting_days }
  • dbt sources point at the marketplace views, never the physical tables, so the semantic layer inherits the same governance boundary.
  • MetricFlow compiles metric requests to Trino SQL, which is what POST /v1/query executes.
One honest limitation. MetricFlow is open source, but the hosted Semantic Layer API (the JDBC/GraphQL endpoint BI tools connect to) is a dbt Cloud feature. Self-hosted, you either run MetricFlow to compile SQL behind your own API — which is what the design above does — or you accept dbt Cloud for that endpoint. Worth deciding before promising BI tools a native semantic-layer connection.
