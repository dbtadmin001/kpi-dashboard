02

How change data is captured

Capture is log-based, not query-based. SQL Server CDC writes every insert and update into capture tables from the transaction log; Debezium reads those and publishes one event per row change. The application is never polled and never carries a last_modified column for the pipeline's benefit.

  • Snapshot, then stream. snapshot.mode=initial reads current table state once (events marked op=r), records the log position, then switches to streaming inserts (op=c), updates (op=u) and deletes (op=d). Verified: 9,062 source rows produced exactly 9,062 snapshot messages.
  • Every intermediate state is captured. An application moves RECEIVED → IN_REVIEW → COMPLETED as three revisions, and all three reach the lake with before/after images. This is the property an hourly batch cannot reproduce — see section 04.
  • Least privilege. nda_debezium has SELECT only, plus membership of the CDC gating role. A separate nda_simulator writes; a third principal, nda_erasure, is the only one that may DELETE.
  • Ordering is per key. Topics are partitioned by record_id, so all revisions of one record land on one partition in order. There is no global ordering guarantee and none is needed.
Two things bit us here and are worth writing down. Debezium needs SELECT on the whole cdc schema, not just the gated _CT tables — it reads cdc.captured_columns to build schemas, and without it every snapshot crashes. And deleting Kafka's internal Connect topics while the worker is running puts it into a crash loop; stop the worker first.

Keeping producer and processor in step

Nothing in this chain assumes a message is delivered exactly once. Instead, every stage is idempotent, so re-delivery converges to the same state. That is what makes the guarantee hold across restarts — and this pipeline restarted many times during the build.

How we check it rather than assume it. Two independent reconciliations run against the live system: source row counts against Kafka high-watermarks per topic (9,062 = 9,062), and Trino's gold KPIs against a Python recomputation from SQL Server (258 series, 0 differences). The second is the strong one — it re-derives every indicator by a different code path and compares values, numerators and denominators.

Honest limit: cross-table consistency is eventual. Each Iceberg table commits on its own checkpoint, so a query spanning nine tables can catch them at slightly different moments. The serving API pins each table to a specific snapshot id and returns those ids in _meta.snapshots, so a report is reproducible and says so, rather than claiming an atomicity it does not have.
04

Streaming versus an hourly batch

The honest framing: for these KPIs, hourly batch would be cheaper, simpler and almost as fresh. Regulatory turnaround times are measured in weeks; nobody decides anything differently because a number is 45 seconds old instead of 45 minutes. Streaming earns its place here for one specific reason, and it is not latency.

CDC streaming in use

  • Freshness 15–60s, bounded by the checkpoint interval.
  • Captures every state transition — queue time, rework, how long work sat in each status.
  • Near-zero source load: reads the log, never queries the tables.
  • Cost is always-on: ~5.6 GB RAM for Flink + Kafka + Connect, running whether or not data arrives.
  • Failure recovery needs checkpoint and state reasoning; a bad deploy can corrupt state.
  • Backfill is bounded by Kafka retention (7 days); older replay means re-snapshotting.

Hourly batch not chosen

  • Freshness up to 60 min — perfectly adequate for these indicators.
  • Sees only the latest row state. An application that went RECEIVED → IN_REVIEW → COMPLETED inside one hour arrives as "COMPLETED", and the intermediate durations are gone forever.
  • Repeated extraction queries load the transactional database during business hours.
  • Cost is burst: compute only while the job runs. Materially cheaper.
  • Failure recovery is trivial: rerun the window.
  • Backfill is unlimited — rerun any window straight from the source.
The deciding factor is measurement, not speed. The bottleneck analysis in this dashboard reports touch_days and wait_days per process step — how long work was actively handled versus sitting in a queue. Those numbers only exist because CDC records each status change as its own event with its own timestamp. An hourly snapshot would show the same final turnaround totals but could never decompose them, and the "where is the delay?" question is the one the regulator actually wants answered.

If that decomposition were dropped from scope, hourly batch would be the correct choice for this workload and would remove roughly two-thirds of the moving parts.

Lineage

Implemented with OpenLineage, the vendor-neutral standard, and published to both servers from one graph definition: Marquez for the raw events, and OpenMetadata for the catalog UI, where lineage sits beside the glossary and the GDPR classification. Because the graph is derived from the pipeline's own contract, neither copy can drift from the code.

GDPR governance

Classification lives in code, not a spreadsheet, so every control derives from one declaration and drift is detectable. The audit fails if any column reaches the lake unclassified. The same declaration is pushed into the catalog, so what the business reads in OpenMetadata is what the pipeline enforces: 111 columns across 28 tables carry PII.Sensitive, PII.NonSensitive or PersonalData.Personal, and each lake table is tagged with its medallion layer.

Erasure, verified end to end

A subject holding 2 applications and 65 rows across seven tables was erased: 32 source rows deleted, and within 30 seconds CDC had carried the deletions through every silver and gold table. Subject access then returned nothing.

The trap in a lakehouse: a delete is not an erasure. Iceberg keeps snapshots, so a deleted row stays readable through time travel until snapshots expire. Erasure is only complete after expire_snapshots runs over every affected table, and the tooling says so in its output rather than reporting success early. The second trap is direction: deleting in the lake alone is undone by the next CDC snapshot — the source must be deleted first.

Masking keeps identifiers joinable without exposing them: the same entity hashes to the same value, so cohort analysis still works on the masked view, but no analyst sees an applicant identity.

Asynchronous enrichment

Some report attributes — an applicant's legal name, country, registry standing — come from a slow external registry. Putting that call in the streaming path would let a third party's latency stall a Flink checkpoint. So it runs out of band.

321Entities per pass
11.6sWall clock, concurrency 24
16×Faster than sequential
20Failures recorded, not dropped

The pattern, and the four properties that make it safe to depend on:

  • Bounded concurrency. A semaphore caps in-flight calls, so the enricher cannot overwhelm the registry or its own event loop.
  • Per-call timeout and retry with backoff. One slow entity delays only itself.
  • Failure is a row, not a gap. An unreachable entity is written with status='unavailable'. You can see what is missing and why, and retry it later.
  • Reports LEFT JOIN the dimension. A pending entity reads as NULL with a reason. The report never blocks waiting for enrichment, and never invents a value.

Of 639 applications, 599 are enriched and 40 read as pending — the report renders correctly either way. If enrichment ever needs to be inline rather than out of band, the streaming equivalent is Flink's async I/O operator, which applies the same bounded-concurrency and timeout discipline inside the job rather than beside it.

How the simulation behaves

The simulator backfills history on an accelerated clock, then hands over to real time once it reaches today. After that, applications arrive on real dates at a realistic cadence rather than the simulation racing into the future.

Duplicate protection. Nine per-table primary keys cannot express uniqueness across processes, so an intake registry holds every application id under a single primary key. A submission checks it first for a friendly rejection; the primary key is what makes a duplicate actually impossible under concurrency. Tested against re-submission, cross-process collision, and collision with a simulator-generated id — all rejected.

Who may see what

Identity and authorization are deliberately separate services. Keycloak answers only who you are and which group you are in; Open Policy Agent answers only what that group may do. Both are generated by Terraform from a single map in infra/variables.tf, so a group cannot exist in identity without a matching policy, or gain data access without an identity.

Which two indicators the public sees, and why

Service-delivery timeliness only: new applications evaluated on time and decisions granted within 90 days for MA; new trials evaluated on time and registry submissions on time for CT; facilities inspected on time and reports published on time for GMP.

Compliance and CAPA indicators are deliberately withheld. pct_facilities_compliant, pct_gcp_compliant and the CAPA measures report failure rates over small cohorts of named facilities and trials. Published quarterly at this granularity they invite re-identification of who failed an inspection, which is a reputational and legal exposure the timeliness measures simply do not carry. Timeliness says how well the regulator performed; compliance says who broke the rules.

Where it is enforced

  • The API is the enforcement point, not the UI. The dashboard renders only the tabs the entitlement allows, but every export re-checks with OPA, so a tampered browser gains nothing.
  • Tokens are verified against the realm's public keys, not by calling introspection. Tokens live 10 minutes, which bounds how long a revoked session stays usable.
  • An unreachable policy engine denies. OPA failing closed is the only safe default; an authorization service that fails open is worse than none.
  • Unknown groups get nothing. A group the policy does not recognise contributes no entitlement rather than being treated as a wildcard.
Not yet enforced at the query engine. Trino is shared with the atc-poc project, and its access control is engine-wide, so switching it to OPA would also govern their catalogs. Anyone holding Trino credentials can therefore still query any table directly. Closing that gap means either a dedicated Trino for NDA or an agreed cutover with that project.

Running more than one pipeline

No second pipeline should rebuild Spark, Trino or MinIO. This one proves the point: the NDA stack builds zero images — every service runs an upstream tag, and it consumes the object store, table catalog, query engine, lineage server and catalog that already existed, by DNS name on a shared Docker network.

TierServicesInstancesHow pipelines are separated
Shared platform
always one		 MinIO, Iceberg REST catalog, Trino, Marquez, OpenMetadata, Airflow, Keycloak 1 Namespaces, schemas, warehouse prefixes, realms and roles — not separate servers
Shared runtime
one cluster, many tenants		 Kafka, Debezium Connect, Flink 1 Topic prefixes, one connector per source, one Flink job per pipeline on a session cluster
Pipeline-specific
unavoidable		 The source system itself (here, SQL Server) N Each pipeline captures a different system of record; nothing to share
The mechanism is three lines of Compose. Every pipeline joins the same external network instead of creating its own, and then addresses shared services by their alias (minio:9000, iceberg-rest:8181, trino:8080): 
networks:
  shared:
    external: true
    name: ${SHARED_NETWORK:-atc-poc_pipeline_net}

What a second pipeline actually costs

  • New containers: only its source database, if it has one. Kafka, Connect and Flink should take another tenant rather than another cluster — a topic prefix, a connector, a job.
  • New images to build: none. Everything here is an upstream tag.
  • New isolation: an Iceberg namespace trio, a Trino schema set, a Keycloak group, an OPA entitlement, an S3 prefix. All configuration, no infrastructure.
Where this deployment is not yet that. Kafka, Connect and Flink currently sit in the NDA Compose project, so a second pipeline would be tempted to start its own. They belong in the shared platform project and should be promoted there before pipeline two, not after — moving a broker with live topics is far more disruptive than starting it in the right place. Note also that the biggest images on this host are two custom Spark builds totalling 12.1 GB for what is one engine, alongside three separate Postgres instances backing Airflow, Marquez and OpenMetadata. That is where the duplication actually is.

Capacity was the binding constraint. The medallion job runs 57 operators in one TaskManager, and each Iceberg writer buffers on the Java heap. It OOM-crashed repeatedly until managed memory was cut from 40% to 10% — this job's keyed state is tiny, and the default reservation was starving the part that matters. Parquet row groups were also cut from 128 MB to 8 MB and S3 multipart buffers from 32 MB to 5 MB. The Docker VM has since been raised from 15.5 to 21.5 GB via .wslconfig, which is what lets the pipeline and the full catalog run together: 16.3 GB in use, 5.2 GB free. The host has 31.8 GB, so roughly 9 GB is left for Windows — workable, but not generous.
